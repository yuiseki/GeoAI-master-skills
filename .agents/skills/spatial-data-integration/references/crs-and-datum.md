# 座標系と測地系

数字は 2026-10-14 に pyproj 3.8.0 (PROJ 9.8.1) で測り、`scripts/test_geometry_facts.py` に残した。

## 地理座標系と投影座標系

- 地理座標系 (EPSG:4326、EPSG:6668 など) は、楕円体の上の経度と緯度 (度)。度は長さではない。経度 1 度の長さは緯度で変わる (赤道で約 111 km、北緯 60 度で約半分)。
- 投影座標系 (UTM、平面直角座標系、等積の EPSG:6933 など) は、平面のメートル。どの投影も、距離、面積、方向の全てを同時には保てない。

| 測りたいもの | 向く座標系 | 向かないもの |
|---|---|---|
| 面積 | 等積 (EPSG:6933、各地域の Albers など) か、楕円体の上で計算 | Web メルカトル (EPSG:3857)。面積は北緯 35.7 度で約 1.52 倍、60 度で 4 倍 |
| 距離 | 楕円体の上の測地線 (pyproj の Geod)、狭い範囲なら UTM や平面直角座標系 | Web メルカトルのメートル。東京と大阪は測地線で 403.8 km、Web メルカトルで 493.8 km (22% 長い) |
| 方向、形 | 正角 (メルカトル、UTM) | 等積 |

Web メルカトルは地図のタイルのための座標系で、解析の座標系ではない。

## 測地系 (datum)

測地系は、楕円体と、それを地球に置く基準。同じ経度と緯度でも、測地系が違えば地上の別の点を指す。

- 旧日本測地系 (Tokyo datum、EPSG:4301) と世界測地系 (JGD2011、EPSG:6668) は、東京駅で 463.5 m ずれる。古い地図や古い座標を、測地系を変換せずに重ねると、これだけずれる。
- JGD2011 と WGS 84 の変換は、PROJ では 0 m (同じとして扱う)。実際の差は数 m 以下で、多くの分析では無視できるが、測量の細かさでは無視できない。
- JGD2000 と JGD2011 は、2011 年の東北地方太平洋沖地震で地殻が動いた地域で異なる (配布元によれば東北地方で最大数 m。このリポジトリでは測っていない、未確認)。
- 地殻はプレートの動きで年に数 cm 動く。WGS 84 や ITRF のような地球全体の座標系では、座標に時点 (coordinate epoch) が付く。数 cm の精度が要る分析 (測量、GNSS の比較) でだけ問題になる。

測地系の変換には、グリッドや変換のパラメータが要ることがある。変換の手順は pyproj の `Transformer.description` で確かめる。

## 水平と鉛直

- 標高 (海抜、ジオイド高からの高さ) と、楕円体高 (GNSS が直接出す、楕円体からの高さ) は違う。差はジオイド高で、日本では数十 m (このリポジトリでは測っていない、未確認)。GNSS の高さと地図の標高を混ぜない。
- 鉛直の基準 (東京湾平均海面など) も測地系の一部。

## 座標の順

- EPSG:4326 の公式の座標の順は「緯度、経度」。GeoJSON や多くのライブラリは「経度、緯度」。pyproj で `always_xy=True` を付けずに EPSG:4326 から変換し、経度、緯度の順で渡すと、緯度 139.77 度として読まれ、結果は無限大 (inf) になる。エラーにならず、無限大や海の上の点が返る。
- DuckDB の `ST_Transform` も、EPSG:4326 では `always_xy := true` を付ける。

## 確かめ方

1. 読んだデータの座標系の名前と、座標の範囲を書く (経度なら −180〜180、日本なら 122〜154)。
2. 2 つのデータを重ねる前に、同じ地物 (駅、交差点) で位置を比べる。数百 m ずれていれば測地系、緯度と経度が入れ替わっていれば座標の順を疑う。
3. 距離と面積は、測りたいものに合う座標系で測り、使った座標系を書く。
