# analysis-reporting

答えを読む人は、まず結論を知りたい。次に、その結論をどこまで信じてよいかを、データと方法から判断したい。このスキルは、分析の段階で既に出た数字と来歴 (データの名前と版、実行したコマンドと設定) を、最終回答の決まった枠に並べる。新しい計算はしない。答えに書く数字は、分析の出力にある数字だけ。

| reference | 中身 |
|---|---|
| [levels](references/levels.md) | 詳細度の 3 段階 (簡単、標準、重い) の選び方、段階ごとに足すもの、実際の分析の出力から書いた例 |
| [github-markdown](references/github-markdown.md) | GFM と GitHub 独自の数式・Mermaid の記法、公式文書 |
| [figure-led-report](references/figure-led-report.md) | 重い分析の report.md。結論を要点の表、読み手ごとの表、図ごとの読み方、読み方で変わる答えの表の順に組む |

ひな形は [assets/answer-template.md](assets/answer-template.md)。

## 固定する構造

全ての答えに、この順で 4 つを置く。見出し (`## 問い`) でも、行頭のラベル (`問い: …`) でもよい。

1. 問い: 何を調べたか。1 行。依頼の言葉を、調べた対象と範囲がわかる形に言い直す。
2. 結論: 答え。数字には単位と、あれば幅 (区間、ばらつき) を付ける。結論が条件つきなら、条件も結論に書く (「2 つの記録が独立なら 476」)。問いの言葉の読み方 (何を数えるか、どの範囲に入れるか、値をどう対応づけるか) で答えが変わるなら、主にした読み方とその答えに、読み方を変えたときの答えを並べる。
3. データ: 使ったデータセットの名前と版 (または取得日)、範囲 (場所と期間)、使った件数と除いた件数。版がわからなければ「版は未確認」と書く。
4. 方法: どう調べたか。手順と、結論を左右する設定 (半径、帯域、分け方、閾値)。

5 つ目の「確かめていないこと」は、結論の読み方を変える未確認のことがあるときに足す。重い分析では必ず書く。

## 形式

答えと報告は、GitHub 上で読める Markdown で書く。基本の見出し、表、画像などは GitHub Flavored Markdown (GFM) に従う。数式と Mermaid は GitHub 独自のレンダリングを使う ([github-markdown](references/github-markdown.md))。依頼が「可視化して」「地図にして」でも、HTML のページ、ノートブック、PDF を答えにしない。動かせる HTML の図は、頼んだ人がそれを求めたときだけ作り、答えとは別のファイルにしてリンクする。

表現は内容から選ぶ。1〜2 文で明確なら本文だけにし、使えるという理由で表や図を足さない。

| 示すもの | 選ぶ表現 |
|---|---|
| 少数の値の正確な比較 | Markdown table |
| 指標、推定量、距離、目的関数、正規化など、量の定義 | 数式。既に分析で使った量やモデルだけを書き、記号の意味を最小限の本文で定義する。複雑な式は fenced `math` block を使う。実際のパラメータ値、単位、条件も隠さない |
| 実際のデータフロー、処理手順、依存関係、採用した分析設計・因果構造 | fenced `mermaid` block。分析していない処理や因果関係を描かない |
| 分布、比較、時系列、残差、地図など、実測値や空間分布 | 既存の分析・可視化出力の PNG を `![説明](outputs/map.png)` で貼る。報告時に作り直さない |

表、数式、Mermaid、PNG は、本文より短く正確に伝わる場合だけ使う。同じ内容を本文・表・図で繰り返さない。数式で後付けの権威付けをせず、Mermaid を装飾や値の大小・分布の表現に使わない。Mermaid は Matplotlib の代わりではない。簡単な答えを図や数式で長くしない。

## 手順

1. 分析の重さを決める ([levels](references/levels.md))。
   - 簡単: 1 つのデータを数える、引く、1 つの値を答える。
   - 標準: 手法を 1 つ選んで当てた。
   - 重い: モデル、因果、推論、複数の手法の比較、確かめの段階がある。
2. 結論に使う数字を、分析の出力 (ツールの結果、ログ、表) から拾う。拾えない数字は書かない。足りなければ、分析の段階に戻って出す。ここで計算し直さない。
3. 4 つの枠を埋める。データの版と件数、方法の設定は、出力やコマンドに書いてあるものを写す。分析中に起きたこと (除いた行、止まった理由、外れた仮説) のうち、結論の読み方を変えるものだけを残す。流す前に書いた計画と実行の記録があれば、結論ごとに確認 (規則を先に決めた比較) か探索かと、計画から変えたこと (何を見た後に、何を、なぜ) を、記録から写す。記録が無いなら、事後に思い出して確認と書かない。
4. 重い分析の report.md は、結論の枠を要点の表から図へ降りる形に組む ([figure-led-report](references/figure-led-report.md))。
5. 段階の長さに収める。簡単なら全体で 8 行まで、標準なら 40 行まで。表の行、数式・Mermaid のフェンスと中身も空でない行として数える。収まらないなら、重さの見立てが違うか、結論に関係しないことを書いている。
6. 確かめる。答えを Markdown のファイル (`.md`) に書き、出力とコマンドを別のファイルに集めて、`scripts/check_report.py` に渡す。

```sh
python3 scripts/check_report.py tmp/answer.md --level simple --evidence tmp/outputs.txt
```

check_report.py は、答えが Markdown のファイルで、HTML のページの記法 (`<html>`、`<body>`、`<script>`、`<div>` など) を含まないこと、4 つの枠があること、その順序、問いが 1 行であること、データに版か日付があることを確かめる。重い段階では「確かめていないこと」があること、段階ごとの行数の上限も確かめる。`--evidence` を渡すと、結論の数字が出力に現れるかを、結論の側の桁で丸めて確かめる (82% は 0.8183 に合う。0.45 は 0.4446 に合わない)。日付は数字として数えない。

`projects/<名前>/report.md` を書いたら、プロジェクトのフォルダごと `scripts/check_project.py` に渡す。証拠を自分で集めて渡す手間が無く、渡し忘れも起きない。

```sh
python3 scripts/check_project.py projects/<名前>
```

check_project.py は、`outputs/` の UTF-8 のテキスト (CSV、JSON、TXT、ログ、Markdown) と、報告がリンクする別のプロジェクトの `outputs/` を証拠にして、check_report.py の確認を全て流す。加えて、報告の中の相対リンクと画像の参照先が存在すること、プロジェクトのテキストのファイルが全て UTF-8 であること、`README.md` があることを確かめる。`outputs/` の外 (`artifacts/` など) の数字を使ったなら、そのファイルを `--evidence` で足す。

数字の照合が ok でも、数字が正しいとは限らない。小さな数や短い小数は、出力のどこかの別の値と偶然に一致しうる。照合が見つけるのは、出力のどこにも無い数字だけ。要点の表の数字は、どの出力のどの値かを自分で辿れるようにしておく。

テストは `uvx --with pytest pytest scripts/test_check_report.py scripts/test_check_project.py`。

## やらないこと

- 数字の計算し直し、結論の強化。出力に無い効果の大きさや有意を足さない。
- 来歴の全ての記録 (コミット、全ての設定、派生物の系図)。この MVP の範囲の外。
- 簡単な問いへの、背景、文献、限界の長い節。
- 地図の凡例や metadata の詳細。地図を答えに含めるなら、値の単位、CRS、区切り方、データの版を図の近くに書く。

## 書き出すもの

- 4 つ (と、必要なら 5 つ目) の枠の答え
- `check_report.py` (report.md なら `check_project.py`) が ok を返したこと。返さなかった項目を残すなら、その理由
