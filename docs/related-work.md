# 関連するスキル集とライブラリ

GeoAI-master-skills の外にある、地理空間のスキル集とライブラリ。中身は写していない。使うときは、それぞれのライセンスと、測った環境を確かめる。

検討して取り込まなかったもの (見送ったもの) も、読んだ版、見送った理由、取り込むならどこか、とともにここに書く。同じものを何度も検討し直さないため。新しいものを検討する前に、まずここを探す。

## isaaccorley/geospatial-skills

- 場所: <https://github.com/isaaccorley/geospatial-skills> (2026-10-14 に a203446 を読んだ)
- ライセンス: このリポジトリで書かれたスキルは Apache-2.0。取り込んだスキルは、元のライセンス (Apache-2.0 の portolan-skills、MIT の opengeos/geoai-skills) のまま。
- 中身: 19 のスキル。GDAL、GeoParquet、GeoZarr、PMTiles、STAC のカタログ、衛星画像の取得など、データを作って配る側の道具が多い。
- GeoAI-master-skills との違い: GeoAI-master-skills は、何を測るか (評価の分け方、リーク、空間の自己相関) と、データの罠が中心。向こうは、大きなジョブを壊さずに流す技術が中心。特に `parallel-geospatial`、`planet-bulk-download`、`pmtiles-pipeline` に、実際のジョブの失敗から書いた、次のような知見がある。
  - 独立に分けられる軸 (地域、タイル、ヒルベルト順) で分けて、プロセスプールで流す。
  - 1 行ずつ追記する JSONL に完了を記録して、途中から再開できるようにする。
  - 一時ファイルに書いてから置き換える。ラッパーから `--force` を渡さない。
  - exit 139 (segfault) と exit 137 (メモリ不足で強制終了) の読み方。
- 数字は向こうの環境 (96 コアのノード、DuckDB spatial 1.5.0 のころ) のもの。版が違うと当てはまらないことがある。例: 向こうは「1,500 万行の `ST_Touches` の自己結合は segfault する」と書く。こちらで DuckDB 1.5.6 (CPU 8、メモリ 16 GB の Docker) で測ると、OSM の建物 2,990 万行 (osm-japan-src-2026-08) の自己結合が 50 秒で終わり、segfault しなかった (2026-10-14)。

## GRIND-Lab-Core/night_owl_research_agent (NORA)

- 場所: <https://github.com/GRIND-Lab-Core/night_owl_research_agent> (2026-10-16 に 5f7a246 を読んだ。この commit の日付は 2026-05-05)。論文は arXiv:2605.02092。
- ライセンス: README は MIT と書き、`LICENSE` を見るように言うが、5f7a246 には `LICENSE` のファイルが無く、GitHub もライセンスを検出していない (未確認)。中身は写さない。
- 中身: GIScience の手法の集まりではなく、研究の進め方全体 (文献の調査、着想、実験、査読、報告書と論文) を Claude Code の上で回す research-agent の harness。`skills/` に 22 のスキルと知識のファイル、フック (セッションの終わりに引き継ぎのファイルを書く)、書き手と評価する側を分けるきまり、人の確認で止める印 (`HUMAN_CHECKPOINT`) がある。
- `spatial-analysis` のスキル: 562 行の 1 つのスキルに、問いの分類、データの準備 (CRS、品質、結合)、空間の重み、ESDA、回帰、予測、到達性、内挿、時空間、診断と頑健性、地図、報告をまとめている。手順ではなく、判断の表とガードレールとして書かれている。
- GeoAI-master-skills との共通点: 問いから手法を決める。経緯度で距離を測らない。原因を言うのに相関を使わない。値の意味が違うもの (件数と率) を混ぜない。数字は実行した結果から書く。
- GeoAI-master-skills との違い: GeoAI-master-skills は、答える問いごとに小さなスキルに分け、全体の流れはリポジトリ直下の AGENTS.md が受け持つ。NORA は 1 つの大きなスキルに空間の分析をまとめ、論文までの流れは別のスキルと harness が受け持つ。数字の扱いも違う。NORA の表は既定の閾値 (特徴量の数、標本の数の上限、p 値の区切り) を置くが、GeoAI-master-skills は、手法ごとに小さな既知解と仮定を崩した合成データで振る舞いを測り、その結果を reference に書く。
- 参考にする点:
  - 個別の空間手法に進む前に、そもそも空間の手法が要るかを判定する。座標を持つことは理由にならない。
  - 診断は、全てを流す checklist ではなく、問い、手法、データに応じて選ぶ。
  - 問いに答えられる最も軽い分析を選ぶ。
  - 行った診断と頑健性の確認に加えて、検討したが行わなかったものと、その理由を残す。
  - 内挿面、予測の地図、補完、模擬、生成した背景点などの派生物を、観測と区別する。後段がそれを観測と取り違えないように、作り方を残す。
  - 報告の数字を、それを出した実行に結び付ける。
- そのまま取り込まない点 (NORA の固定の規則と、GeoAI-master-skills の決め方):
  - 特徴量は 15 まで、GWR は 5,000、MGWR は 3,000 件まで、のような固定の閾値。計算の上限は環境の事情で、手法の決まりではない。
  - 結合するデータの時点の差が 2 年を超えたら印を付ける、という固定の線。差が効くかは、現象がその間に変わるかで決まる。
  - VIF が 10 を超えたら落とす、という一律の規則。共線性が問題かは、係数を説明に使うか、予測に使うかで変わる。
  - 点の重みは k = 5〜8 の最近傍、という固定の選び方。重みは、相互作用の届く範囲の仮定から決め、変えて結論が保たれるかを見る。
  - Moran's I を p 値だけで強い、中程度と分けること。大きさと、重みの選び方による変わり方を並べる。
  - 空間データなら行の無作為な交差検証は禁止、という一律の規則。評価の分け方は、予測する場所と観測の離れ方 (使い道) から決める。
  - 件数は必ず人口で割る、という一律の規則。割る分母は、問い (率か量か) と、記録の過程 (観測の努力) から決める。人口で割ることは観測の偏りの補正ではない。
  - 空間の重みは常に行で標準化する、という規則。標準化は統計量の意味を変える (隣の数が違う単位の扱い) ので、選んだ理由を書く。
  - 来歴を記録する `.meta.json` の形式そのもの。GeoAI-master-skills は、まず記録すべき項目をきまりとして置き、形式は既存の成果物に合わせて決める。

## GeoLarryLai/pyGeoMapper (見送り)

- 場所: <https://github.com/GeoLarryLai/pyGeoMapper> (2026-11-16 に README だけを読んだ。最新の commit は a227358、2026-11-13。リポジトリは 2026-10-31 に作られた)。PyPI と conda-forge の `pygeomapper`。
- ライセンス: AGPL-3.0-or-later。Apache-2.0 のこのリポジトリにはコードを写せない。使うなら、pip で入れて呼ぶか、引用している論文の手法を自分で書く。
- 中身: 衛星画像と DEM から、地表の変化と地質を地図にする Python (中身は Rust) のライブラリ。
  - 地表の変化: DEM の差分、Sentinel-2 と Landsat の分光指数 (NDVI、NBR、NDWI など) の変化、Sentinel-1 LiCSAR の InSAR、ITS_LIVE の氷河の速度。地すべり、山火事、洪水、地震、氷河の例。
  - 地質図: AlphaEarth の 64 次元の年ごとの埋め込みを使った教師あり学習。地質図の北西の半分で学習し、南東の半分で試して正解率 91.0%、macro-F1 0.89 (作者の値。こちらでは流していない)。
  - 断面図と 3D のブロック図。
- 作者自身が「実験的で、十分に検証していない」と書いている。
- 見送った理由: オープンデータ版の Playground の 3 つの領域 (POI、道路、地上の画像) に当たらない。AGPL で、コードを取り込めない。
- 取り込むなら: 近いのは `sar-change-detection` (InSAR、変化)、`terrain-hydrology` (DEM)。埋め込みで地質図を作り、地域を分けて試す形は、評価の分け方の例として参考になりうる。見直すなら、そのときの最新の版を読み直す。

## atsushi-green/ds-ai-coding-skills (一部を取り込んだ)

- 場所: <https://github.com/atsushi-green/ds-ai-coding-skills> (2026-11-16 に 9494b02 (2026-10-03) を読んだ。README、`predictive-modeling-diagnostics` の SKILL.md と `references/ml-evaluation.md`、`analysis-reporting`、`statistical-ml-review`、`scripts/skill_eval/README.md` と `cases.yaml` の冒頭)。解説は Zenn の 2 本の記事 (README から辿れる)。
- ライセンス: MIT。中身は写していない。
- 中身: 地理に限らない、データ分析のための AGENTS.md と skills。
  - 基本の skill: Python、SQL、polars、可視化、パスと入出力、Notebook、報告、レビュー。
  - `*-diagnostics` の 5 つのルーターと 19 の手法の references (統計的推論、予測モデル、因果推論、教師なしと EDA、シミュレーションと最適化)。手法を実行したら、頼まれなくても「必ず出す図」と「必ず出す値 (合格基準と違反時の対処)」をそろえさせる。報告には `| 診断項目 | 実測値 | 合格基準 | 判定 | 次アクション |` の表を載せる。
  - 発火テストのハーネス (`scripts/skill_eval/`): ケースごとに別の `claude -p` を起動し、stream-json から読んだ skill と references を取り出す。種別は explicit、implicit、scope (部品として使う手法で、別の references まで読まないか)、negative。
- GeoAI-master-skills と同じ所: 発火テストを transcript から判定する。explicit、implicit、negative、forbid の考え方。依頼にスキル名を書かない。
- GeoAI-master-skills に無く、参考になる点:
  - 読了から実行へ: references を読んでから最初の Python を実行したかを、transcript の順序で数える。取り込んだ (2026-11-16、`evals/trigger.py order`)。こちらの E2E のログに当てると、4 つの実行が全て、主なスキルの reference を最初の Python の前に読んでいた。それまでの記録の「後の段の reference を開かなかった」は、glob での読み取りを見落とした誤りだった。
  - variants と covers: references の中で手法や条件ごとに分かれる「必ず出す図」を分岐として宣言し、全ての分岐がどれかのケースで試されているかをテストで確かめる。reference に行を足すとテストが落ち、ケースの足し漏れに気づける。reference の単位で取り込んだ (2026-11-16)。新しい reference に発火テストのケースが無いと `evals/test_trigger.py` が落ちる。始めた時点で 199 のうち 180 にケースが無く、`evals/trigger_uncovered.txt` に並べた (減らすだけの一覧)。reference の中の分岐までは宣言していない。こちらの reference には「必ず出す図」の表が無いため。
  - 判定と次アクションの文をコードの if で組み立てない。コードは値を表で出すだけで、判定は報告で、基準と図を見て書く。
  - scope の種別: 部品として使う手法 (傾向スコアのロジスティック回帰、クラスタの図の PCA など) で、その手法の reference まで読まないか。
  - 「必ず出す図」を実データで出して並べたギャラリー。
- そのまま取り込まない点:
  - 合格基準の固定の線 (名目のカバレッジ ± 5% など)。GeoAI-master-skills は、基準を手法ごとの既知解と合成データで測って reference に書く。
  - 評価の分け方の決め方。向こうはグループ、時間、不均衡で選ぶ。地理の分析では、予測する場所と観測の離れ方 (空間の自己相関) が加わる (`cross-validation-design`、`leakage-audit`)。
  - 1 ケースごとの費用の上限 (5 ドル) と、Claude Code だけで流すこと。こちらは 4 つの CLI で比べ、Docker の中で流す。

## global-hydrodynamics/CaMa-Flood_v4 の visualization (検討した。取り込みは未決)

- 場所: <https://github.com/global-hydrodynamics/CaMa-Flood_v4/tree/manual-automation/visualization> (2026-11-16 に manual-automation の 6037115 (2026-11-15) を読んだ。`visualization/README.md`、`figure_making_guideline.md`、`cmf_colormap/README.md`、`river_map/README.md` の見出し)。CaMa-Flood は全球の河川と氾濫原の水理モデル。モデル本体は読んでいない。
- 自身の注記: この可視化は v5 の作業で作られた参考資料で、v4 の配置と出力では確かめていない。最新は cmf_v5_beta にある。
- ライセンス: Apache-2.0 (リポジトリと `cmf_colormap` のどちらも)。中身は写していない。
- 中身: メコン川を例にした図のギャラリー (河道網のラスタ、線、ベクタ、集水域、高解像度の背景、流量、浸水面積、浸水深) と、図を作るきまり (`figure_making_guideline.md`)。背景と重ねる層を考えて作った 6 つの配色 (`cmf_colormap`)。
- GeoAI-master-skills (`analysis-visualize`) と同じ所:
  - 比べる地図は同じ範囲と色の範囲にする。
  - 欠損を 0 にしない。
  - 河道の線は、上流の面積の小さいものから描き、太い本流を上に重ねる (こちらの `network-map` では低い階級から描く)。
  - 背景に対して、主役の層が目立つ配色にする (こちらは背景との明るさの差で検査する)。
- こちらに無く、参考になる点:
  - 地図の枠を先に決める: 地図の軸の大きさと縦横の比を先に決め、題、色の帯、凡例は枠の外に足す。並べる図は画像の縁でなく地図の枠をそろえ、画像を縮めてそろえない。`bbox_inches="tight"` や `tight_layout()` で、図ごとに枠が動かないようにする。色の帯の無い図にも同じ幅の空き (見えない色の帯) を取る。そろったかを、保存した画像の画素で確かめる。
  - 色の帯の長さを、対応する地図の軸の長さに合わせる。
  - 向きのある線: 向きは接続のデータから取る。合流点で矢印が重なるなら、印を線に沿って動かすか繰り返し、線の形は変えない。正負のある流れ (逆流) を、中央から分かれる色と矢印で描く。範囲が正負で非対称なら、0 の近くだけ線形の対数で正規化する。こちらの `network-map` は、有向の辺の矢印を「まだできないこと」としている。
  - 範囲の全ての網を描くと言うなら、密度を下げるために線を間引かない。一部なら選び方を書く。
  - 時間の定義 (ある時刻の値、期間の平均、積算、最大) を、題か注記で区別する。
  - クラスの地図で、意味のある 0、割り当てのない単位、範囲の外、欠損の印を、別のものとして描く。
  - 図の中の題を、図の番号から始める (図だけが切り出されても、どの図か分かる)。
- そのまま取り込まない点:
  - 虹のような配色 (Shade-Rainbow、Diverge-Rainbow など)。こちらは、明るさが値の順に並ばない虹色を止めている。向こうも、重ねる層での目立ち方を優先し、知覚の一様さと色覚の多様性とは引き換えだと書いている。
  - 設定をシェルのスクリプトに置き、描く処理を Python に置く分け方。こちらはスクリプトの引数と、PNG と同じ名前の JSON で来歴を残す。
  - ギャラリーへの載せ方と、図の PNG を git で追跡すること。こちらは成果物を artifacts に置き、リポジトリに入れない。
